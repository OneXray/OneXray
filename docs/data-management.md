# 数据管理

## 原库升级

`schemaVersion` 固定为 3，只保留正式旧库 v1/v2 → v3 的一次性升级。
同一个 App 版本内的破坏性结构改动直接更新当前 schema，不增加开发版本迁移分支。
路由配置表使用 `RoutingProfile`，表与数据类沿用 Drift 默认命名，不使用 `DataClassName`。
不兼容的开发库由开发者在停止 App/VPN 后删除旧数据库文件或卸载 App 重建；App 不自动
删库，不尝试降级或修补开发库。

数据库文件在冷启动前已不存在时不属于版本迁移：`StoragePreparation` 直接创建 schema 3，
并向 Geodata 发布流程传递明确的“数据库本次启动前不存在”信号。该信号只用于收敛文件与
新数据库状态，不增加 migration 分支。

首次业务访问前由 `StoragePreparation` 打开数据库并完成必要迁移，不依赖 VPN 查询、停止或轮询，
不生成升级前 SQLite 副本。数据库直接拒绝不支持的版本，以及已有业务表但版本为 0 的未知数据库；
新文件或未完成首次创建留下的空库可正常初始化。结构修改与版本提升在同一事务完成；
已有 ID、订阅关系、Base64 内容及 Age 密钥保持不变，不做全量编码转换。
`setting/full` 退休行不进入新业务；所有旧 Raw 保留，包括超过新增上限的情况。
从旧产品模型升级时重置运行偏好，已有订阅缓存及有效 Geodata 原位复用。
旧库只记录自定义 Geodata；启动校验确认默认文件、自定义文件和索引组成完全匹配的旧平铺发布后，
只补充默认数据的 manifest 记录，不重新复制或下载文件。文件不完整或出现未登记文件仍保持失败。
节点的旧测速缓存重置为未检测，由现有测速队列补测，不修改节点内容或订阅归属。
迁移只执行必要的结构修改、旧测速缓存重置和版本提交，不在运行时复制全表作逐值比较；数据保留由
隔离的旧库测试核对，迁移失败由 SQLite 事务回滚。打开失败后释放连接，不标记存储就绪；
修复问题后可重新打开并重试。

不要对主用户数据执行验证迁移，使用隔离样本。真实旧库样本与安装包升级须单独验收。

## UI 数据订阅

与 UI 绑定的 CoreConfig 列表及节点存在状态使用数据库 Stream，通过页面 Cubit 更新 UI，
页面销毁时取消订阅。outbound 列表统一在查询中按 `delay` 升序排列，测速更新后自动重排；
位置、订阅分组内的节点及收藏列表沿用这一顺序。Raw 列表维持原来的 ID 顺序。

订阅列表由 `SubscriptionDao.allRowsStream` 按 ID 升序推送，新增、编辑、删除后通过同一页面
Cubit 自动更新分组、来源名称及管理列表，不依赖手动刷新。单个订阅编辑和后台任务仍使用一次性查询。

单个节点/配置继续使用一次性查询，不绑定 Stream；编辑草稿不被数据库刷新覆盖。
启动、保存、删除及测速任务中的事务读取也保留一次性查询。

## 测速、下载与操作状态

所有手动、自动及排队测速统一发布到 `AppEventBusState.pinging`；订阅、Geodata（包括
Raw/自定义路由导入的依赖）和 App 版本信息下载统一发布到 `downloading`，不提供静默下载
开关。并发下载使用任务计数，全部结束后才清除状态；失败也必须释放计数。

测速请求统一按提交顺序执行；多个订阅分别入队，位置或多节点请求也按订阅拆分原生批次，
不得同时测速不同订阅。保留同一订阅内每批最多 5 个节点，批次完成后写入数据库。
自动测速在正常服务就绪后启用；服务就绪时按数据库中的未检测状态补测，覆盖上次中断的
未检测节点，不另存待测速列表。Setup 不提供节点导入，也不依赖或启动测速。
连接、Geodata 文件访问和测速分别使用独立的 `CommandSerialExecutor` FIFO 实例，只
复用排队实现，不合并成全局队列；队列中的失败不阻断后续任务。下载、测速与普通配置保存
不互相等待。

不再使用全局 `DataMaintenance` 或异步上下文继承登记。收藏使用单次 SQL，复制节点的
读取和插入使用同一个数据库事务，订阅编辑只保存来源设置。普通保存只经过所属模块的
事务或连接队列，不因其它模块的任务登记而等待。

订阅下载、确认后的导入提交、Geodata 更新各自记录模块内正在执行的操作；清空流程通过
这些模块的暂停接口等待它们结束，不把普通数据库操作纳入全局登记。自动更新在当前来源
结束后停止后续来源；测速在当前原生批次完成并写入后停止，尚未开始的批次及队列请求取消。

VPN 状态同步、metrics 读取不进入业务命令队列，清理时通过连接命令状态使旧回调失效。
用户确认在提交前完成，提交时再核对原配置。Geodata 暂存下载不修改正式文件，
只使用自身文件协调；取消或替换导入草稿负责释放暂存目录。

相关页面订阅这两个状态展示 loading，页面跳转不会丢失后台任务提示。页面自己的操作标识
只负责定位按钮、阻止保存等操作重复提交和分别取消手动测速请求，不替代共享的网络活动状态。
共享 loading 不锁住整页，也不替换节点的更多菜单；设置/只读页面可以在导航栏展示活动状态。
保存配置及其他本地 I/O 使用各自的操作状态，不借用 `downloading`。

隧道、日志等保存沿用按钮自身的 loading，并在连接队列取得执行权后重新核对原配置；若
清理或其它操作已更改配置则拒绝覆盖。清空期间不排队等待保存：未开始的连接命令取消，
新命令直接返回失败；清理结束后可重新操作，不能在清理之后自动执行旧保存或启动请求。

## Geodata 发布

默认 `geoip.dat` 与 `geosite.dat` 是一组，只能一起更新且不能删除。自定义数据按文件名
保存，支持 HTTPS 添加、更新和删除，不提供本地导入。添加成功即有效，不加“可用”标签。

`VpnConstants.datDir` 是 App 管理的唯一 Geodata 读写目录。所有 DAT、同名 JSON 分类索引
及 `timestamp.txt` 都直接平铺在该根目录，不创建子目录。下载可以先写入
`datDir` 的同级临时目录，由 libXray 校验 DAT 并生成索引；校验成功后再替换根目录文件并
提交数据库元数据，任一步骤失败都恢复原文件。

Geodata 复用独立的文件访问队列，协调正式目录的读取、发布、删除、失败清理，以及相关
配置校验和连接准备/启动。下载和暂存文件索引在队列外执行，不占用全局队列，也不等待
无关测速。默认组仍一起发布；数据库事务与文件访问按“先文件队列、后数据库事务”组织。

Raw JSON 与自定义路由导入只在同级临时目录下载和校验。完成用户确认后才发布正式文件。
Geodata 导入模块统一执行发布、保存、完成或失败回滚，调用方只将依赖元数据写入纳入现有
配置数据库事务，不分别调用发布、提交、回滚方法。文件队列覆盖整个保存过程，不能在发布
文件与提交元数据之间允许其它读取、更新或连接启动插入。

页面只持有配置导入草稿和依赖声明，不持有 Geodata 文件发布句柄；分享只读取依赖声明。
取消时清理暂存文件，保存失败回滚正式文件且保留可重试草稿。暂存目录同时作为未完成发布
的最小日志：下次冷启动按数据库 manifest 完成已提交发布，或清理未提交文件。

准备或启动 VPN 时不复制、下载或更新 Geodata，Xray 运行环境直接读取 `VpnConstants.datDir`；
启动前仍通过 libXray 校验本地配置，缺少或损坏的必要文件明确报错，不通过联网下载兜底。
已启动的核心继续使用启动时已加载的规则，文件更新供后续启动使用。删除自定义数据时
同时删除根目录中的 DAT 与索引。

macOS System Extension 是唯一明确例外：由于跨容器边界，允许沿用现有 Swift 实现向扩展
传输 Geodata。该传输只属于原生平台桥接，不引入第二套 App 侧读写目录；真实按需启动及
扩展消息链路的设备验收与普通文件事务测试分开记录。

### 冷启动重建

- 数据库文件丢失后新建 schema 3 时，旧平铺目录中的文件已经失去 manifest。删除这些
  orphan 文件，并从 App 资源重新发布默认 `geoip.dat` / `geosite.dat` 组；不尝试推断或
  合并自定义数据。
- 整个 `dat` 根目录缺失，或目录为空但数据库仍有发布元数据时，清除不可恢复的 Geodata
  元数据并重新发布默认组。
- 部分文件损坏、默认组不完整、存在嵌套文件，或者数据库仍存在且没有明确丢失信号时出现
  orphan 文件，均保持失败。此类状态需要显式处理，不能通过启动流程静默合并或清理。

上述恢复只处理完整存储单元丢失，使用内置资源且不发起下载。自定义 Geodata 无法从已丢失
的数据库 manifest 或已删除的数据目录恢复。

## 自动更新

数据更新位于高级的 Xray 运行与诊断，订阅与 Geodata 分别保存自动开关和 24/72/168 小时
周期。启动、前台恢复、每小时与真实连接边沿触发到期检查；重复 connected 不反复调度。
订阅自动更新不要求 VPN 已连接。Geodata 自动更新只在已确认 VPN 连接时执行：未连接时，
启动、前台恢复和定时检查均跳过 Geodata；连接成功后沿用延迟 3 秒的到期检查，期间断开
则取消本次延迟任务。App 重开时沿用初始化已确认的连接状态，不为自动更新增加 VPN 轮询。
等待订阅更新结束后以及每个 Geodata 数据源开始前重新检查连接状态；断开后不再发起后续
数据源更新，已开始的单次更新按原有文件事务完成或回滚。更新失败保留旧文件，只记录更新
错误，不修改 VPN 状态、不触发重连。手动更新及配置导入依赖下载不受此自动更新条件限制。
所有订阅统一遵循全局开关和周期，不保存或展示订阅级自动更新开关；导入数量与识别失败数只用于本次操作反馈，不落库。
到期检查串行运行，独立自定义数据不会因默认组更新失败而被长期跳过。更新不重新选择
本次运行节点。测速只暴露超时与 URL，沿用自动队列，不暴露并发数量/自动测速开关。

## 清理数据

App 不提供备份、备份导入与恢复；普通节点、订阅、Raw JSON 和自定义路由的导入/分享保持独立。

清理全部数据时，登录项注销和清理后就绪要求见 [启动的清理与失败边界](app-startup.md#清理与失败边界)。

`AppDataCleanupService` 统一负责清理协调：先同时暂停自动更新、订阅导入/下载、测速和
连接命令以及 Geodata 更新，再等待必要的在途操作。批量导入不再继续下一个来源，不再
为刚完成的导入提交后台测速；不要求把所有排队节点测完。
取得 Geodata 文件队列后，先确认原生 VPN 停止，再清空数据库、运行文件和偏好并重建默认
数据。停止失败不继续删除。无论清理成功或失败，都恢复各模块接收新操作；自动测速原有
启用状态不因清理改变。旧响应必须在清空前完成提交或被取消，不能在清空后回写。

## 实现入口

- 启动存储准备与缺库信号：`lib/service/launch/storage_preparation.dart`
- 旧库升级：`lib/core/db/database/database.dart`
- 数据发布：`lib/service/advanced/xray/geodata/service.dart`
- 更新：`lib/service/advanced/xray/data_update/scheduler.dart`、`lib/service/advanced/xray/data_update/service.dart`
- 清理：`lib/service/settings/data_cleanup.dart`
