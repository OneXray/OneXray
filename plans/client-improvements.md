# 客户端体验增强分阶段计划

状态：P1/P2 代码与自动验证已完成，提交记录见 Git 历史；P3–P4 未开始。
核对日期：2026-09-22；正式数据库基线为 `v26.9.4` 的 schema 5。

本文件用于后续按阶段执行，不代表已上线功能。当前行为以 [文档索引](../docs/README.md)
中的合同为准；各阶段完成后再同步对应合同，不提前把计划写成现有能力。

## 1. 目标与顺序

继续保持新手友好、界面克制，高级能力通过 JSON 和 AI 工具承载。
优先减少套餐状态不明确、配置难以修正和网站无法访问时难以定位原因的问题。

| 顺序 | 阶段 | 交付内容 | 当前状态 |
| --- | --- | --- | --- |
| P1 | 订阅套餐信息 | 套餐元数据读取、缓存、列表摘要和详情 | 已实现，自动验证通过；设备验收待执行 |
| P2 | JSON 纠错体验 | 错误定位、原因展示和轻量字段补全 | 已实现，自动验证通过；设备验收待执行 |
| P3 | 配置校验 CLI | 复用 App 配置处理的命令行入口及结构化结果 | 未开始 |
| P4 | 目标网站诊断 | 主动目标检查，区分节点探测、规则推断和真实会话 | 未开始 |

四阶段分别实施、分别验收，可以独立发布。P2 与 P3 共享配置处理及错误结果，
但不要求一起发布；P4 在接入页面前必须先完成真实检测链路的最小验证。

不纳入本轮：运行中自动故障隔离、按 Wi-Fi 切换配置、订阅下载路径选择、
脚本执行、远程控制、常驻诊断监控、支持包及额外日志脱敏。
不恢复累计流量、macOS 菜单栏网速、启动失败回滚或普通节点导入二次确认。

## 2. 执行规则

1. 后续获得实施授权后按 P1 → P2 → P3 → P4 推进，只执行当次授权范围。
   阶段内按下列步骤完成检查，不提前接入尚未验证的后续生产入口。
2. 开始一个阶段时，重新核对当前源码、已发布版本和本计划基线。若其他任务已实现部分内容，
   先验收再复用，不按旧计划重复实现，也不覆盖用户现有改动。
3. 遇到测试或编译错误、技术验证无法达到核心目标、需要新增权限或改变已确定的产品行为时，
   停在相应步骤说明问题。不能以降级展示冒充验收通过，也不能自行扩大为上游内核改造。
4. 每阶段记录实际修改、检查命令与结果、未覆盖平台和剩余事项。按阶段提交获授权后，
   验证通过即提交本阶段实际修改的仓库；涉及 OneXray 和 libXray 时分别提交，
   未改动的仓库不创建空提交。push、PR 和发布按用户当次授权执行。
5. Demo、隔离样本和运行证据放在工作空间 `references/client-improvements/`，不用系统临时目录，
   不读取或修改开发者主数据库。Demo 仅验证风险点，不建设第二套产品实现。
6. Flutter/Dart 命令全局串行。Android 模拟器允许启动 VPN；macOS 不启动 VPN、不截屏；
   Windows/Linux 不在当前主机强行编译运行。遵循 [验证边界](../docs/refactor-validation.md)，
   将本地测试、模拟器、真机、平台构建和发布验收分别记录。
7. UI 沿用共享主题、页面内局部 loading 和现有导航方式，同时核对紧凑与桌面布局。
   既有文案复用批准的翻译，新文案随功能补齐现有语言；不顺带修改无关页面。

## 3. P1：订阅套餐信息

### 确定的产品范围

- 从订阅响应的 `Subscription-Userinfo` 读取上传、下载、总量和到期信息；记录信息获取时间。
- 在订阅列表提供一行摘要，例如“剩余 42 GB · 12 天后到期”；详情展示具体数据和获取时间，
  复用现有订阅分组详情，不为元数据建立新的服务商中心。
- 随现有手动、自动订阅更新刷新，不增加独立定时器、额外后台请求、刷新周期或功能开关。
- 提供方未返回的数据不伪造；未提供额度与明确无限额度必须区分，不能把缺失值默认当作无限。
- 元数据缺失或解析失败不得阻断有效节点导入；更新失败保留旧信息及其原获取时间，
  不把旧数据展示为本次成功获取。过期、用尽仅作提示，不禁用连接、不删除节点。
- 套餐信息来自提供方，不是 App lifetime 统计，不与本次连接上下行相加，也不加入连接配置备份。
- 不解析订阅正文中的节点名称来猜套餐，不增加单节点 hash、新增/变更数量或识别失败计数。

### 开发步骤

1. 明确响应头解析与展示规则，包括单位、时间、部分字段缺失、零值、超额和格式错误。
   这些规则集中在套餐信息处理模块；服务商约定不明确时展示未知，不猜测无限或过期。
2. 定义最小可空存储及获取时间；在现有下载结果中传递元数据，复用订阅事务、请求失效和
   Stream 更新机制。明确成功响应不含元数据、修改订阅 URL 后旧缓存的处理，
   避免旧套餐被标为新来源或新一轮的有效数据；不得破坏 HWID 拒绝及零可用节点保旧规则。
3. 实施正式数据库升级。若开发时当前 schema 仍为 5，则新增结构使用 6，并覆盖已发布 v5
   及仍受支持的更早版本升级路径；保留节点、订阅、Age 密钥、HWID 和连接配置。
   不写 v5 内修补，不让用户以卸载重装替代正式升级。若其他功能已提升 schema，先重新核对。
4. 列表与详情消费同一份套餐数据，保持原有排序、菜单和连接操作；状态提醒不改路由或运行配置。
5. 完成针对性测试和页面核对，更新订阅、数据管理、导航合同，确认备份仍排除这类缓存。

### 验收标准

- [x] 普通、明确无限、已过期、已用尽、部分字段缺失和错误响应通过解析与 Widget 测试。
- [x] 元数据解析失败时有效节点仍可导入；网络、HWID 拒绝和零可用结果不破坏旧节点。
- [x] 更新失败不刷新套餐获取时间；切换来源和迟到响应不会把旧套餐覆盖到新来源。
- [x] 列表由数据库变化自动更新，没有新增后台轮询或影响 VPN 状态的行为。
- [x] 隔离的 v1–v5 schema 样本可升级，新安装可建库，原有连接资产与密钥保持不变。
- [x] 套餐信息不进入备份，不改变现有导入确认、节点保护及自动测速规则。
- [x] 紧凑/桌面布局、五种语言、长数值和 2× 字号通过 Widget 布局测试。
- [ ] Android 模拟器/真机视觉检查及真实旧安装包升级验收（与以上自动测试分开）。

## 4. P2：JSON 纠错体验

### 确定的产品范围

保留 `re_editor` 和现有高亮、行号、括号配对、保存校验，先改错误呈现，再补轻量输入提示。
覆盖节点、自定义路由相关 JSON、高级路由和完整 Raw 的现有编辑入口，不改变各自的导入类型。

- JSON 语法错误有可靠 offset 时显示行列并定位；有可靠字段路径时定位相关字段。
- 内核仅返回文字原因时完整显示并允许复制，不伪造错误位置，不降为笼统“保存失败”。
- 错误结果与当前编辑文本对应；失败不丢草稿，旧异步结果不标记到新文本的错误位置。
- 补全先覆盖常用字段、枚举值和已有 tag 引用，并按编辑类型区分上下文。
- 补全仅为提示，不成为新的字段拒绝清单。协议配置继续由 libXray 判断，
  App 只保留既有名称、导入类型及管理字段约定；不重写 Xray 协议校验。
- 不要求首版覆盖所有 Xray 字段，不自动重排或裁剪 Raw/高级 JSON，不顺带替换编辑器。

### 开发步骤

1. 盘点现有语法 offset、字段路径、libXray 错误和页面呈现，将已有信息组织成 UI/CLI
   可复用的最小结果。只保存真实可得的原因与位置，不为每个错误造一套分类框架。
2. 接入共享编辑器的定位、标记与复制，验证行列计算、编辑后标记失效及失败保留草稿。
3. 补充当前类型的轻量字段与引用提示；提示缺失或滞后不能使合法高级字段无法输入和保存。
4. 对现有编辑入口和保存流程回归，更新配置、导航合同及必要的使用说明。

### 验收标准

- [x] 语法错误与可定位的字段错误能准确定位；不能定位时保留完整原因。
- [x] 编辑、校验失败、复制错误和再次保存不丢草稿或改变未修改配置的语义。
- [x] 未知高级字段不因补全未覆盖而被拒绝，协议判断与原有 libXray 校验一致。
- [x] 现有节点、常规/高级路由、Raw 保存流程正常，结构化诊断不依赖页面；CLI 宿主仍需 P3 验证。
- [x] 移动与桌面 Widget 操作、LTR JSON 与 RTL 界面组合、五语言 2× 字号通过测试。
- [ ] Android/iOS 真正输入法与系统剪贴板、桌面原生运行操作验收（不以 Widget 平台变体代替）。

## 5. P3：配置校验 CLI

### 必须保留的验证层级

| 层级 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 静态检查 | JSON 语法、App 输入类型、必要材料和本地依赖状态 | 内核能够构造或 VPN 能够运行 |
| 配置编译 | 用明确输入生成 App 对应的配置 | 缺失的平台参数、节点或资源自动可用 |
| 内核验证 | 本次验证副本通过构造及关闭检查 | 完整运行配置、监听端口、权限、TUN 或实际联网必然成功 |
| 实际连接 | 通过真实运行获得的检测证据 | 不属于首版 CLI |

`TestXray` 执行 `LoadConfig → core.New → Close`，不调用 `Start`，但可能读取文件、修改 env、
日志/DNS 全局状态，或创建协议特定资源和后台任务；构造失败时部分资源未必可关闭。
因此不得称为安全沙箱、严格离线或无副作用检查。App 的验证副本与运行配置也并非完全相同。
实现依据为 [App 验证投影](../lib/service/shared/xray/validation.dart) 及
[libXray 的现行说明](../../libXray/README.md#testxray)。

### 确定的首版范围

- 先支持桌面命令行，只接收显式提供的配置文件、类型、本地资源目录和必要编译参数。
- 复用 App 的类型处理、编译和验证逻辑，分别支持相应 JSON 类型；不在 Go 或 CLI 中
  重新维护另一套 App 规则，不把裸 Xray 校验成功直接等同于能导入任意 App 编辑器。
- 提供稳定退出码与结构化 JSON 结果，区分检查通过、失败和未执行，并保留具体原因。
- 缺节点、平台参数、Geodata 或证书等必要材料时明确报告，不隐式下载或猜测补齐。
- 不读取用户主数据库，不修改已保存配置或 `run/start.json`，不自动启动 VPN、不上传凭据、
  不开放远程控制端口；编译输出仅写入用户明确指定的目标。
- 首版不提供自动修复/应用配置、MCP 服务或 App 远程启停。

### 开发步骤

1. **先验证运行方式。** 当前编译器间接依赖 Flutter、数据库和 Pigeon，不能直接假设
   独立 `dart run` 可用。用最小验证工程确认纯输入模型、目录参数与 App 适配的拆分范围，
   记录 CLI 宿主、打包方式和各桌面平台可支持程度，再接正式入口。
2. 静态检查与编译只消费显式输入，复用 P2 的错误信息；不为 CLI 拉起整套 App 初始化、
   授权、数据库、自动更新或测速流程。
3. 内核验证优先采用独立进程，处理退出和异常；进程隔离不等于禁止文件或网络副作用。
   验证副本过滤与 App 保持一致，结果说明本次检查层级和未验证事项，不干扰正在运行的实例。
4. 固定命令合同、退出码和机器可读格式；普通节点、常规路由、高级路由和完整 Raw
   各使用共享的有效/无效样本验证 UI 与 CLI 结果一致性，不只覆盖一种配置。
5. 完成本地说明与可复制示例；后续对外文档再说明 AI 如何读取结果和修正配置，
   不在尚未提供工具时宣称已完成自动验证闭环。

### 验收标准

- [ ] 在目标运行方式下可以处理显式文件，不依赖已安装并初始化的用户 App 数据。
- [ ] 相同输入、类型和验证参数在 UI 与 CLI 得到一致结果，缺材料时不隐式补齐。
- [ ] 退出码、结构化输出、原始错误和可得的位置稳定；未执行检查不算通过。
- [ ] 原始配置与 App 管理字段过滤后的验证副本可区分，不承诺启动或联网必然成功。
- [ ] 核心验证不会操作当前 VPN 实例；不读取主库或写入正式运行文件。
- [ ] 测试副作用、当前可验证平台、尚待构建/实机验收平台都有明确记录。

## 6. P4：目标网站诊断

### 确定的产品范围

提供一个用户主动使用的目标检查入口，输入域名或 URL，按需查看结果及技术详情。
不增加后台采样、常驻面板或未经用户触发的测试请求；不自动修改配置或重启 VPN。
入口位置与最终页面在完成技术验证后确定，复用现有导航和错误展示。

结果必须分成三类，不以其中一类替代另一类：

1. **指定节点探测**：这个节点能否访问给定目标。现有 `pingBatch` 只提取 outbounds，
   忽略输入中的路由和 DNS 等根级配置，不能用来证明当前 VPN 的实际分流。
2. **规则推断**：在给定上下文下配置预计匹配什么规则。需要考虑规则顺序、条件组合、
   Geodata、DNS、端口与协议等；上下文不足时明确显示不能确定。
3. **真实会话证据**：当前 VPN 实际使用的路径及检测结果。只有拿到真实运行证据时才展示；
   命中 `proxy` balancer 不等于已确定具体节点，单次出口 IP 也不代表多节点全部流量。

### 开发步骤

1. **先验证检测链路。** 明确测试请求由哪一个进程/入站发出、使用哪份 DNS/路由、
   是否真正经过当前 VPN。核对可以复用的核心能力，不在 Dart 重写完整路由匹配器。
2. 用受控样本区分节点访问失败、DNS 异常和规则导致的路径差异，确认能可靠报告的阶段。
   地区查询失败不等于节点不可用，HTTP 状态异常也不能一律归为 VPN 故障。
3. 在能力可证实后确定首版页面，分别展示事实、推断和未知；无法提供真实分流证据时，
   不把普通节点测速改名为“VPN 分流诊断”交付。需要改变核心目标时先修订计划。
4. 复用现有网络活动状态和操作反馈；检查结束、失败或取消后释放本次操作状态。
   不影响当前连接，也不增加新的全局任务锁。
5. 完成 Android 实际链路验证；桌面需要 VPN 的分支保留人工验收，更新功能与验证说明。

### 验收标准

- [ ] 三类结果都有明确来源和上下文，静态规则推断不会冒充真实命中。
- [ ] 受控正常/失败样本能够验证检测链路；错误原因不被统一压成“连接失败”。
- [ ] FakeDNS、DNS 二次匹配、多节点等无法确定的部分明确标为未知，不猜实际出口。
- [ ] 只在用户触发时检查，结束后没有额外常驻任务，不改配置或触发 VPN 重连。
- [ ] 不把一次成功检查表述为所有网站可用或绝对无 DNS 泄漏；未覆盖平台单独记录。
